# AI 基础概念速查表

> 来源：AI × Web3 School — 个人学习笔记
> 日期：2026-05-24
> 目的：建立 Agent、workflow、AI coding 和工具调用的共同语言

---

## 1. LLM（大语言模型）

**一句话解释：** 一个在海量文本上训练出来的神经网络，给它一段文字（prompt），它能预测并生成接下来的文字。

**具体例子：**
Claude、GPT-4、Gemini 都是 LLM。你对它们说"帮我写一封请假邮件"，它们会生成一段符合语境、语法正确的邮件内容——不是从模板库找的，是实时"生成"的。

**常见误区：**
- LLM 不是数据库，它不"记住"你的数据——每次对话都是独立的，它没有长期记忆
- LLM 生成的内容是"概率预测"，不是绝对事实，可能一本正经地胡说八道
- 它不知道自己的知识截止日期之后发生的事（除非接入实时工具）

---

## 2. Prompt（提示词）

**一句话解释：** 给 LLM 的输入文本，是你"指挥"它做什么的方式。

**具体例子：**
```
# 角色
你是一个资深产品经理。

# 任务
为一个 Web3 钱包设计登录流程。

# 要求
分步骤说明，重点关注安全性。
```

这段文字就是一个 prompt。prompt 越清晰、角色越明确，LLM 的输出质量越高。

**常见误区：**
- prompt 不是"越短越聪明"——复杂任务需要详细指令
- 同一个 prompt 在不同模型上效果可能差异很大
- 把私密信息放进 prompt 是很常见的隐私风险（LLM 会记录日志）

---

## 3. Context Window（上下文窗口）

**一句话解释：** LLM 一次能处理和记住的文本总量，包括你的输入和它的输出。

**具体例子：**
Claude 3.5 的上下文窗口是 200K tokens，约等于一本《傲慢与偏见》的长度。你可以在一次对话里粘贴一整份代码让它 review，或者上传一整段文档让它总结。

**使用边界：**
- 超出上下文限制的内容会被"遗忘"——LLM 看不到窗口之外的部分
- 超长上下文会显著拖慢响应速度和增加 token 消耗
- 超过上下文限制时，需要用分块（chunking）+ RAG 等策略来处理

---

## 4. Workflow（工作流）

**一句话解释：** 一个由多个步骤组成的任务执行路径，LLM 按顺序完成每个步骤，最终产出结果。

**具体例子：**
"写一篇 Web3 科普文章"的工作流：
```
Step 1: 搜索最新 Web3 新闻（搜索工具）
  ↓
Step 2: 提取关键事件和趋势（LLM 分析）
  ↓
Step 3: 生成文章大纲（LLM）
  ↓
Step 4: 逐段撰写正文（LLM）
  ↓
Step 5: 检查事实准确性（LLM + 搜索对比）
```

整个过程不需要人工介入每一步，但人类在关键节点可以介入确认。

**常见误区：**
- 工作流不等于 Agent——工作流是固定的流程，Agent 有自主决策能力
- 复杂工作流需要仔细设计每个节点的输入输出格式
- 工作流中某个步骤失败会导致整个链条中断，需要错误处理机制

---

## 5. Agent（智能体）

**一句话解释：** 能够自主感知环境、做出决策、执行动作的 LLM 系统——它不只是响应一次 prompt，而是循环思考→行动→观察结果→调整下一步。

**具体例子：**
一个 Web3 研究 Agent：
```
感知：读取钱包地址和链上活动数据
思考："这个地址最近交互了哪些合约？DeFi 还是 NFT？"
行动：调用 Etherscan API 获取交易历史
观察：发现该地址大量使用 Aave 借贷协议
决策：继续查询 Aave 的清算记录
...
（持续循环直到任务完成）
```

Agent 的核心循环：**感知（Perceive）→ 思考（Think）→ 行动（Act）→ 观察（Observe）**

**常见误区：**
- "加了 tool use 就等于 Agent"——不一定，需要有自主决策才算
- Agent 也会犯错（hallucination），关键操作必须有 guardrails
- Agent 的能力上限由 tool 决定——给它更多工具，它能做更多；没有工具，它只是普通聊天

---

## 6. Tool Use（工具调用）

**一句话解释：** 让 LLM 能够执行外部操作（搜索、计算、调用 API、读写文件），把"说话"变成"做事"。

**具体例子：**
你问 Agent："以太坊现在 gas 多少？"
Agent 调用 gas 追踪 API → 返回实时数据 → 给你一个准确的数字。
这个过程不是 Agent"记住"的，是它调用了工具查出来的。

常见的 LLM 工具调用协议：
- **MCP（Model Context Protocol）**：Anthropic 提出的开放标准，让 AI 工具互操作
- **OpenAI Function Calling**：GPT 系列调用外部函数的标准化方式
- **LangChain Tools**：Python/JavaScript 中的工具封装方式

**使用边界：**
- 工具调用有延迟——不是实时的，需要考虑超时处理
- LLM 对工具返回结果的理解受上下文窗口限制
- 工具描述（tool description）需要写清楚，输入格式不对会导致调用失败
- Web3 场景下，Agent 调用钱包签名需要额外的授权和安全设计

---

## 7. AI Coding（AI 辅助编程）

**一句话解释：** 使用 LLM 来帮助写代码、review 代码、调试和解释代码。

**具体例子：**
- **写代码**：让 Claude 帮你实现一个 ERC-20 代币合约
- **Review**：粘贴代码让 AI 检查漏洞和安全风险
- **Debug**：贴错误日志，让 AI 定位问题
- **解释**：读不懂某段合约代码，让 AI 逐行解释

常见工具：Claude Code、Copilot、Cursor、Windsurf

**常见误区：**
- AI 写的代码**必须人工 review**——它不了解你的具体业务逻辑
- AI 不了解你的代码库架构（除非接入 RAG 或代码索引工具）
- Web3 合约代码尤其危险——AI 可能生成有漏洞的代码，上链后无法修改
- AI 适合做**增量开发**，不适合做**架构设计**

---

## 8. Guardrails（安全护栏）

**一句话解释：** 对 LLM 输出或行为的约束机制，防止 Agent 做不该做的事。

**具体例子：**
一个 Web3 Agent 的 guardrails：
```
- 禁止转账超过 $100 的资产（除非人类确认）
- 禁止调用未经白名单的合约
- 禁止在主网执行任何操作（强制测试网优先）
- 禁止透露私钥或助记词相关的内容
```

**常见误区：**
- guardrails 不是 100% 可靠的——LLM 仍可能通过 prompt injection 绕过
- guardrails 需要在系统层（基础设施）+ 应用层（prompt 设计）双层设置
- Web3 Agent 的 financial guardrails 尤为重要，误操作可能导致真实资产损失

---

## 9. Human-in-the-Loop（人工介入）

**一句话解释：** 在自动化流程的关键节点设置人工确认步骤，由人来做最终决策。

**具体例子：**
一个 DeFi Agent 执行大额交易的工作流：
```
1. Agent 分析链上数据
2. Agent 生成交易建议
3. 发送通知给人类："建议在 Uniswap 将 1000 USDC 换成 ETH，是否确认？"
4. 人类确认 → Agent 执行
5. 人类拒绝 → 流程终止
```

**使用边界：**
- 不是每个操作都需要人工介入——太小太频繁的确认会造成"确认疲劳"
- 高风险操作（资产转移、合约部署、跨链）通常需要强制人工确认
- 完全自动化的 Agent 在 Web3 领域风险极高，建议至少在高价值操作上有人工介入

---

## 10. Tracing（链路追踪）

**一句话解释：** 记录 Agent 每次决策和 tool call 的完整过程，方便事后复盘和调试。

**具体例子：**
一次 Agent 交易优化的 tracing 记录：
```
[Step 1] LLM: 分析当前 gas 价格
[Tool Call] etherscan_gas_api → 返回 gwei: 25
[Step 2] LLM: 判断 gas 价格偏高，建议等待
[User Override] 人类：仍然执行
[Step 3] LLM: 生成交易签名请求
[Tool Call] wallet_sign → 返回 tx_hash: 0x8f3a...
[Step 4] LLM: 监控上链状态
...
```

**常见误区：**
- tracing 不是日志（log）——日志是分散的事件记录，tracing 是关联后的完整因果链
- 没有 tracing 的 Agent 等于黑箱——出了问题是无法定位的
- Web3 场景下，tracing 记录对于安全审计和资产追回至关重要
