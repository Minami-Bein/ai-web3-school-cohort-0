# 受限 Web3 助手设计说明

> 来源：AI × Web3 School — 个人学习笔记
> 日期：2026-05-25
> 目的：设计一个 AI / Agent 辅助 Web3 操作的工作流，明确 AI 的能力边界和人工门槛

---

## 1. 这个助手解决什么问题

Web3 用户在进行链上操作时，面临两个核心矛盾：

**矛盾 1：操作复杂 vs 风险高**
- 查询余额、规划步骤、检查风险——这些重复性工作浪费用户时间
- 但自动化意味着把签名权限交给 AI——等于把资产完全暴露给一个可能出错或被攻击的系统

**矛盾 2：AI 能力 vs 资产不可逆**
- 区块链交易一旦确认无法回滚（没有"撤销"按钮）
- AI 说"帮你自动转账"——转账是不可逆的，AI 错了就是真钱损失

**这个设计解决的本质问题是：**
在不把签名权限交给 AI 的前提下，让 AI 承担所有可以安全自动化的辅助工作（规划、查询、检查），同时保留人类作为所有写入操作（签名、交易广播）的唯一决策者和执行者。

## 2. 用户输入与输出示例

### 输入示例

| 类型 | 用户输入示例 |
|------|-------------|
| 信息查询 | "我的 Sepolia 钱包余额多少？" |
| 操作规划 | "我想把 0.01 ETH 换成 USDC，帮我规划步骤" |

| 风险评估 | "这个 DApp 让我授权 1000 USDC，安全吗？" |

  □ Gas 费用是否合理

```

人工确认：是否继续授权？
```

## 3. 人工确认点（⚠️ 标记）

完整工作流中的人工确认点：

```
┌──────────────────────────────────────────────────────────────────┐
│ ① 用户输入  →  ② AI 解析  →  ③ 只读执行  →  ④ 生成交易数据       │
│                                                                  │
│  ④ 生成交易数据  →  ⑤ 安全审查  →  ⚠️⑥ 人工确认  →  ⚠️⑦ 钱包签名  │
│                                                                  │
│  ⚠️⑦ 钱包签名  →  ⑧ 交易广播  →  ⑨ 结果验证                      │
└──────────────────────────────────────────────────────────────────┘

⚠️ ⑥ 人工确认（用户必须）
  - AI 暂停，展示交易数据摘要
  - 用户核对：目标地址、金额、Gas 估算
  - 用户明确点击"确认"继续

⚠️ ⑦ 钱包签名（用户必须）
  - 用户在钱包内（Metamask/Argent/Phantom）完成签名
  - AI 无法接触私钥，无法替代这一步
  - 多签钱包需要多个签名者分别确认
```

**关键原则：所有写入操作（转账、approve、部署合约）必须经过这两个确认点。AI 在步骤 ⑤ 完成安全审查后自动暂停，等待人工确认。**

## 4. 风险与限制（至少 3 个）

| # | 风险点 | 说明 | 防御措施 |
|---|--------|------|----------|
| 1 | **Prompt Injection** | 用户输入或外部数据中注入恶意指令，让 AI 执行非预期操作 | 指令边界独立于外部输入；关键操作需用户二次确认 |
| 2 | **钓鱼签名请求** | 诱导用户签名恶意交易（如授权无限额度 approve） | AI 生成签名请求时必须展示完整操作摘要，明确告知授权范围和额度 |
| 3 | **目标地址错误** | 复制粘贴被劫持，资产转至恶意地址，区块链上不可逆 | AI 显示地址前 6 位和后 4 位，人类核对完整地址 |
| 4 | **授权额度失控** | approve() 默认无限授权，合约可转走全部余额 | AI 必须建议有限授权，不提供"无限"选项；提示定期撤销授权 |
| 5 | **恶意 RPC 节点** | 虚假链上数据（假余额、假状态）导致用户做出错误决策 | 多 RPC 交叉验证（至少 2 个独立节点） |
| 6 | **合约未审计** | 调用含漏洞合约，资金不可逆损失 | AI 提供审计状态提示，用户自行判断；优先使用主流协议 |

### 其他限制

- **AI 无法访问私钥**：签名必须在用户本地钱包完成，AI 只能生成交易数据结构
- **交易失败无自动补偿**：交易失败后 AI 可分析原因，但无法自动重试或回滚
- **跨链操作受限**：多链场景下 AI 需要分别连接不同 RPC，配置复杂度高

## 5. 如何验证结果

### 验证三步

```
交易广播后 → 获得 tx hash → 进入验证流程

Step A: 区块浏览器验证
  ↓
  Etherscan / Sepolia Etherscan 输入 tx hash
  核对：
    - 状态：Success ✅ / Failed ❌
    - 事件日志：Transfer、Approval 等事件是否正确
    - Gas used：是否在估算范围内

Step B: 收据核对
  ↓
  对比原始请求 vs 链上执行结果
    - 金额是否一致
    - 目标地址是否一致
    - 合约调用是否正确

Step C: 余额对比
  ↓
  操作前后对比钱包余额
  验证资产变动符合预期
```

### 失败交易处理

```
status = 0（失败）
  ↓
检查 Revert Reason（在 Etherscan 点击 "Jump to trace"）
  ↓
常见原因：
  - Gas 不足 → 增加 Gas 重试
  - Nonce 冲突 → 等待上一个交易确认后重试
  - 合约条件不满足 → 检查合约状态是否满足条件
  ↓
记录失败原因 → 通知用户 → 等待进一步指示
```

### AI 的结果追踪责任

AI 在交易广播后默认行为：
1. 持续追踪 tx 状态（pending → confirmed / failed）
2. 主动报告结果（成功 / 失败及原因）
3. 在获得明确结果前不结束会话

## 受限 AI × Web3 核心原则

```
┌─────────────────────────────────────────────────────┐
│            受限 Web3 助手的核心边界                    │
│                                                       │
│  只读操作（查余额、读合约、查 Gas）→ AI 自动执行       │
│                                                       │
│  写入操作（转账、approve、部署）→                      │
│    AI 生成数据 + 安全审查                             │
│    → 用户必须人工确认                                 │
│    → 用户在钱包内完成签名                             │
│                                                       │
│  签名 ≠ 交易确认                                      │
│  - Sign：证明同意，不付 gas，不改变链上状态            │
│  - Transaction：付 gas，状态不可逆                     │
│                                                       │
│  AI 永远不能：                                        │
│  ❌ 接触私钥或助记词                                  │
│  ❌ 自动完成钱包内的点击确认                           │
│  ❌ 生成无限授权的 approve()                           │
└─────────────────────────────────────────────────────┘
```

## 5 句话总结

**解决什么问题：** 设计一个 AI / Agent 辅助 Web3 操作的受限工作流——AI 负责只读查询、规划生成和安全审查，所有写入操作（签名、交易广播）必须由人工完成，防止 AI 越界执行导致资产损失。

**AI / Agent 辅助的步骤：** 步骤 ② 解析意图、③ 只读执行、④ 生成交易数据、⑤ 安全审查、⑨ 结果追踪——这些是 AI 的核心能力范围，全程不产生链上状态变更。

**哪些步骤必须人工确认：** 步骤 ⑥ 人工复核（用户检查地址、金额、Gas）和步骤 ⑦ 钱包签名（用户点击确认）是不可逾越的人工门槛，AI 无法替代；尤其钱包内签名这一步，任何情况下都不能让 Agent 代为操作。

**如何验证最终结果：** 交易广播后获得 tx hash，在 Etherscan 核对状态（Success/Failed）、事件日志和 Gas 消耗，再对比操作前后钱包余额，确认执行结果与原始意图一致。

**主要风险点：** Prompt Injection（恶意输入让 AI 执行非预期操作）、钓鱼签名请求（诱导 approve 恶意授权）、目标地址被篡改（资产转至恶意地址后不可逆）、授权额度失控（approve 无限授权导致资产可被转走）、恶意 RPC 节点（假余额假状态）。
