# 受限 Web3 助手设计说明

> 来源：AI × Web3 School — 个人学习笔记
> 日期：2026-05-25
> 目的：设计一个 AI / Agent 辅助 Web3 操作的工作流，明确 AI 的能力边界和人工门槛

---

## 一、用户输入

| 类型 | 示例 | AI 处理方式 |
|------|------|-------------|
| **信息查询** | "我的 Sepolia 钱包余额多少？" | 自动执行，只读 |
| **操作规划** | "我想把 0.01 ETH 换成 USDC，帮我规划步骤" | 自动生成计划，待确认 |
| **交易准备** | "帮我生成一笔转账 0.1 ETH 到 0x... 的交易数据" | 生成交易数据，展示，待确认 |
| **合约交互准备** | "我想要调用 Uniswap V3 的 swapExactTokens，帮我准备参数" | 参数解析 + 交易构造，待确认 |
| **风险评估** | "这个合约让我授权 1000 USDC，安全吗？" | 分析授权范围 + 风险提示 |

---

## 二、AI 能做什么（自动执行）

```
✅ 链上只读操作
  - 查询余额、nonce、Gas 价格
  - 读取合约存储（view 函数）
  - 获取交易历史和事件日志
  - 分析 ERC-20 代币信息

✅ 规划与生成
  - 解析用户意图 → 操作序列
  - 构造交易数据（tx struct）
  - 生成签名请求摘要
  - 估算 Gas 费用
  - 生成操作安全报告

✅ 验证与检查
  - 验证目标地址格式
  - 检查合约 ABI 匹配性
  - 多 RPC 交叉验证链上数据一致性
  - 交易发出后追踪状态（pending/success/failed）
```

---

## 三、AI 不能做什么（人工门槛）

```
❌ 私钥 / 助记词接触
  - AI 不能读取钱包私钥，不能生成签名
  - 签名必须在用户本地钱包内完成

❌ 自动触发交易
  - AI 可以生成交易数据，但广播需要用户授权
  - 不能绕过钱包确认界面（Metamask/Argent 等）

❌ API Key 自动写入
  - 第三方 API Key 不能暴露给 AI 自动调用
  - 只能通过用户配置的本地代理或预置凭证调用

❌ 无限授权
  - approve() 授权不允许默认设置无限额度
  - AI 应默认建议有限授权，并明确告知风险
```

## 四、完整 Workflow 详解

```
┌──────────────────────────────────────────────────────────────────┐
│                     受限 Web3 助手完整工作流                       │
│                                                                  │
│  ① 用户输入  → ② AI 解析  → ③ 只读执行  →  ④ 生成交易数据        │
│                                                                  │
│  ④ 生成交易数据  →  ⑤ 安全审查  →  ⑥ 人工确认  →  ⑦ 钱包签名      │
│                                                                  │
│  ⑦ 钱包签名  →  ⑧ 交易广播  →  ⑨ 结果验证                        │
└──────────────────────────────────────────────────────────────────┘
```

### 步骤详解

**① 用户输入**
- 用户发送自然语言请求（通过 Telegram / CLI / Web 界面）
- 触发条件：请求涉及资产操作、合约交互、授权等写入类操作时，需要人工确认

**② AI 解析意图**
- 解析请求类型：查询 / 规划 / 交易准备 / 风险评估
- 识别关键参数：目标地址、金额、合约 ABI、函数选择器
- 分类为只读 or 写入操作

**③ 只读执行（AI 自动）**
- 调用公开 RPC 或预置 API Key 查询链上数据
- 读取余额、nonce、Gas 推荐值、合约状态
- 结果以结构化形式展示给用户

**④ 生成交易数据（AI 自动）**
- 构造交易结构：`to`, `value`, `data`, `gasLimit`
- 计算 Gas 估算
- 生成 human-readable 操作摘要

**⑤ 安全审查（AI 自动）**
```
检查清单：
  □ 目标地址是否在已知恶意地址黑名单中？
  □ 授权额度是否超过必要金额？
  □ 合约是否经过审计（如果是主流协议）？
  □ 操作类型是否为 Swap/Transfer（高风险：Mint/ApproveAll）？
  □ 是否需要多签（资产超过阈值时）？
```

**⑥ 人工确认（用户必须）**
- AI 暂停，等待用户明确确认
- 用户需要：
  - 检查目标地址（复制粘贴，自己核对）
  - 检查 Gas 估算是否合理
  - 确认交易数据正确
  - 明确点击"确认"按钮

**⑦ 钱包签名（用户必须）**
- 用户在本地钱包（Metamask/Argent/Phantom）内完成签名
- AI 无法接触私钥，无法替代这一步
- 如果是多签钱包，需要多个签名者分别确认

**⑧ 交易广播**
- 签名后的交易被广播到区块链网络
- 进入 Mempool，等待打包

**⑨ 结果验证**
```
验证三步：
  1. tx hash 查询 → Etherscan 确认状态（Success / Failed）
  2. 事件日志（event log）→ 确认合约逻辑执行正确
  3. 余额对比 → 操作前后余额变化是否符合预期

失败交易处理：
  - 如果 status=0，检查 revert reason
  - 核对 Gas 消耗是否异常
  - 分析是否需要重试（nonce 冲突等）
```

## 五、风险与限制清单

| # | 风险点 | 说明 | 防御措施 |
|---|--------|------|----------|
| 1 | **Prompt Injection** | 用户输入或外部数据注入恶意指令 | 指令边界独立于外部输入；关键操作需用户二次确认 |
| 2 | **恶意 RPC 节点** | 虚假链上数据（假余额、假状态） | 多 RPC 交叉验证（至少 2 个独立节点） |
| 3 | **钓鱼签名请求** | 诱导签名恶意交易（如 `approve` 无限额度） | AI 在生成签名请求时必须展示完整操作摘要 |
| 4 | **目标地址错误** | 复制粘贴被篡改，资产转至恶意地址 | AI 显示地址前 6 位和后 4 位，人类核对 |
| 5 | **授权额度失控** | `approve` 默认无限授权，资产可被转走 | AI 必须建议有限授权，不提供"无限"选项 |
| 6 | **合约未审计** | 调用含漏洞合约，资金不可逆损失 | AI 提供合约审计状态提示，用户自行判断 |
| 7 | **API Key 泄露** | 第三方服务 Key 在日志中暴露 | API Key 存在本地配置，AI 通过代理调用，不直接暴露 |
| 8 | **交易失败未告知** | AI 生成交易后不追踪结果 | AI 默认追踪 tx hash，直到有明确结果才结束会话 |

## 六、受限 AI × Web3 的关键原则

```
┌─────────────────────────────────────────────────┐
│           受限 Web3 助手的核心边界                 │
│                                                   │
│   只读操作  →  AI 可自动执行，不需确认            │
│   写入操作  →  AI 生成数据 + 安全审查            │
│             →  用户必须人工确认                  │
│             →  用户在钱包内完成签名               │
│                                                   │
│   签名 ≠ 交易确认                                 │
│   - Sign（签名）：证明同意，不付 gas              │
│   - Transaction（交易）：付 gas，状态不可逆       │
│                                                   │
│   AI 永远不能：                                   │
│   - 接触私钥或助记词                             │
│   - 自动完成钱包内的点击确认                      │
│   - 生成无限授权的 approve()                      │
└─────────────────────────────────────────────────┘
```

## 七、5 句话总结

**解决什么问题：** 设计一个 AI / Agent 辅助 Web3 操作的受限工作流——AI 负责只读查询、规划生成和安全审查，所有写入操作（签名、交易广播）必须由人工完成，防止 AI 越界执行导致资产损失。

**AI / Agent 辅助的步骤：** 步骤 ② 解析意图、③ 只读执行、④ 生成交易数据、⑤ 安全审查、⑨ 结果追踪——这些是 AI 的核心能力范围，全程不产生链上状态变更。

**哪些步骤必须人工确认：** 步骤 ⑥ 人工复核（用户检查地址、金额、Gas）和步骤 ⑦ 钱包签名（用户点击确认）是不可逾越的人工门槛，AI 无法替代；尤其钱包内签名这一步，任何情况下都不能让 Agent 代为操作。

**如何验证最终结果：** 交易广播后获得 tx hash，在 Etherscan 核对状态（Success/Failed）、事件日志和 Gas 消耗，再对比操作前后钱包余额，确认执行结果与原始意图一致。

**主要风险点：** Prompt Injection（恶意输入让 AI 执行非预期操作）、钓鱼签名请求（诱导 approve 恶意授权）、目标地址被篡改（资产转至恶意地址后不可逆）、授权额度失控（approve 无限授权导致资产可被转走）、恶意 RPC 节点（假余额假状态）。
