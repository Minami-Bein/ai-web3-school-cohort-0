# 最小 AI × Web3 工作流

> 来源：AI × Web3 School — 个人学习笔记
> 日期：2026-05-24
> 目的：理解 AI 系统和链上操作之间的边界

---

## 一、核心流程图

```
┌─────────────────────────────────────────────────────────────────────┐
│                     最小 AI × Web3 工作流                            │
│                                                                     │
│  ①用户发起任务   ②AI Agent 分析   ③人工复核   ④钱包签名确认   ⑤测试网执行 │
│                                                                     │
│  ──────────────────────────────────────────────────────────────►    │
│   发起方:用户     执行方:AI         执行方:用户   执行方:用户     执行方:网络 │
│                                 ✅必须确认    🔐签名+gas                 │
└─────────────────────────────────────────────────────────────────────┘
```

---

## 二、每一步详解

### Step 1：用户发起任务

| 要素 | 说明 |
|------|------|
| **谁发起** | 用户 |
| **执行方** | 用户（自然语言描述意图） |
| **示例** | "帮我把 0.1 ETH 在 Sepolia 测试网换成 USDC" |
| **是否需要签名/付款** | ❌ 不需要 |
| **是否必须人工确认** | ✅ 是（任务来源必须是人类） |

---

### Step 2：AI Agent 分析

| 要素 | 说明 |
|------|------|
| **谁发起** | 用户触发，AI 自动接续 |
| **执行方** | AI Agent |
| **AI 做什么** | 理解意图 → 规划操作序列 → 调用只读工具读取链上数据 → 评估 Gas 价格 → 生成操作建议 |
| **是否需要签名/付款** | ❌ 不需要（只读操作） |
| **是否必须人工确认** | ❌ 不需要（分析阶段，不产生链上变更） |
| **风险点** | Prompt Injection — 恶意输入可能让 AI 执行非预期操作 |

---

### Step 3：人工复核

| 要素 | 说明 |
|------|------|
| **谁发起** | AI Agent 输出结果后暂停 |
| **执行方** | 用户（必须人工） |
| **复核什么** | 操作意图是否正确、目标地址是否正确、Gas 估算是否合理 |
| **是否需要签名/付款** | ❌ 不需要（仅复核，不触发交易） |
| **是否必须人工确认** | ✅ **必须**（人工确认是安全边界核心） |
| **风险点** | 复核流于形式 — 用户不认真看 AI 输出就点确认 |

---

### Step 4：钱包签名确认

| 要素 | 说明 |
|------|------|
| **谁发起** | 用户确认后触发 |
| **执行方** | 用户（在钱包内主动点击确认） |
| **做什么** | 生成交易请求 → 用户在钱包内查看详情 → 点击签名/确认 |
| **是否需要签名** | ✅ **必须** — 签名在钱包内完成，Agent 接触不到私钥 |
| **是否需要付款** | ✅ 付 Gas（估算费用显示在钱包内） |
| **是否必须人工确认** | ✅ **必须** — Agent 永远不能替代用户在钱包内点击确认 |
| **风险点** | 钓鱼攻击 — 伪造签名请求诱导 approve() 恶意授权 |

---

### Step 5：测试网执行

| 要素 | 说明 |
|------|------|
| **谁发起** | 用户签名后交易自动广播 |
| **执行方** | 区块链网络（节点验证 → 打包 → 区块确认） |
| **做什么** | 交易广播 → Mempool → 验证者打包 → 上链 → 状态写入 |
| **是否需要签名/付款** | ✅ Gas 已由 Step 4 估算并扣除 |
| **是否必须人工确认** | ❌ 不需要（签名已完成，网络自动执行） |
| **风险点** | RPC 节点不可信 — 恶意 RPC 可能返回假数据或不上链 |

## 三、结果验证

```
交易广播后 → 获得 tx hash → 进入验证流程

Step A: 区块浏览器验证
  ↓
  Etherscan / Sepolia Etherscan 输入 tx hash
  核对：状态（success / fail）、事件日志（event）、Gas used

Step B: 收据核对
  ↓
  对比原始请求 vs 链上执行结果
  金额、目标地址、合约调用是否一致

Step C: 余额变动确认
  ↓
  操作前后对比钱包余额
  验证资产变动符合预期
```

## 四、风险点清单

| # | 风险点 | 说明 | 防御措施 |
|---|--------|------|----------|
| ① | **Prompt Injection** | 恶意指令注入用户输入，AI 执行非预期操作 | 指令边界，外部输入不能覆盖核心指令 |
| ② | **钓鱼签名请求** | 伪造 DApp 诱导签名恶意 approve() | 显示完整操作摘要，明确告知授权额度 |
| ③ | **错误目标地址** | 剪贴板篡改 / 复制错误，资产转至恶意地址 | 地址格式校验 + 历史记录匹配 |
| ④ | **恶意授权额度** | approve 不设限，合约可转走全部余额 | 仅授权本次所需数量，定期撤销 |
| ⑤ | **合约未审计** | 调用含漏洞合约，资金不可逆损失 | 仅用审计过的合约，多 RPC 交叉验证 |
| ⑥ | **Gas 估算错误** | Gas 设置过低交易失败，或被恶意超收 | 钱包内查看 Gas 估算，参考多个数据源 |

## 五、Guardrails 原则

| 操作类型 | 处理方式 | 理由 |
|----------|----------|------|
| **只读操作**（查余额、读合约、查 Gas） | AI 可自动执行 | 不改变链上状态，无资产风险 |
| **写入操作**（转账、approve、部署） | 必须人工确认 | 状态不可逆，需人类做最终决策 |
| **授权（approve）** | 明确告知额度，不设无限授权 | approve 是最常见的资产被盗原因 |
| **合约调用** | 仅与审计过的合约交互 | 未审计合约可能含漏洞 |
| **数据验证** | 多 RPC / 多浏览器交叉验证 | 单一数据源可能被篡改 |

## 六、关键区分：签名 ≠ 交易确认

| | 签名（Sign） | 交易确认（Transaction） |
|--|-------------|------------------------|
| **是否付 Gas** | ❌ 不付 | ✅ 付 |
| **是否改变链上状态** | ❌ 不改变 | ✅ 改变 |
| **典型示例** | "Sign to login"（验证所有权） | 转账、Swap、approve |
| **钓鱼风险** | 中（签恶意消息） | 高（签恶意交易） |
| **重要提醒** | 签名前务必看清消息内容 | 确认目标地址、金额、Gas |

> ⚠️ **approve() 授权是最容易被钓鱼的操作** — 授权后合约理论上可以转走你该代币的全部余额，授权 ≠ 转账，但风险更高。

## 七、AI × Web3 最佳实践总结

```
最佳实践：智能分层

  智能账户（限额内）  →  Agent 在设定边界内自主执行
         +
  多签 / 人工确认    →  超限操作必须人类批准
         +
  区块浏览器验证     →  每笔交易可追溯、可核对
```

**核心原则**：Agent 有权做事，但不等同于拥有完全控制权。用合约逻辑给它画边界，而不是把私钥交给它。
