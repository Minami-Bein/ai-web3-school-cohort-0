# Week 2 Module G · Proposal Summarizer 精细化设计

> 从四个选项中选做一个：Proposal Summarizer（提案摘要机器人）
> 精细化设计：数据流 / 输入输出格式 / AI 决策边界 / 状态机 / 标注示例
> 以 Compound Governor + Snapshot 为参考框架
> 输出到 submissions/week2-proposal-summarizer.md

---

## 1. 定位与目标

### 1.1 这个工具解决什么问题

一个活跃 DAO 的成员每天面对的是：

- **信息过载**：一个季度可能有 20~50 个提案，每个提案附带 10~50 条 Forum 讨论
- **时间碎片化**：大多数成员不是全职 DAO 参与者，只能用手机快速浏览
- **决策质量与参与度的矛盾**：不读完全部内容就无法做出知情投票，但读完所有内容需要数小时

**Proposal Summarizer** 的目标：把 30 分钟的提案阅读压缩到 3 分钟的结构化摘要，让成员在手机上 2 分钟内做出"支持 / 反对 / 弃权"的初步判断。

### 1.2 它不是什么

| 它不是 | 为什么 |
|--------|--------|
| 投票机器人 | 它不代替人投票，只是辅助决策 |
| 法律建议 | 它输出结构化信息，不是法律或财务建议 |
| 提案撰写工具 | 草稿生成是另一个工具（Meeting-to-Action）的工作 |
| 实时新闻 | 它处理的是链上已提交的正式提案，不是 rumor 或传闻 |

### 2.2 数据源详细说明

| 数据源 | 数据内容 | 获取方式 | 刷新频率 |
|--------|---------|---------|---------|
| **Snapshot** | 提案标题 / 正文 / 投票结果（支持/反对/弃权票数）| Snapshot GraphQL API | 实时（webhook） |
| **Discourse** | Forum 帖子列表 / 每帖内容 / 回复数 / 作者 | Discourse API | 每 5 分钟轮询 |
| **Discord**（如果有） | #governance 频道的消息 | Discord Bot API | 每 1 分钟轮询 |
| **Governor 合约** | 提案状态 / 票数 / 执行参数 | Alchemy / Infura RPC | 实时 |
| **Etherscan** | 提案创建者地址的历史交易 | Etherscan API | 按需 |

### 2.3 数据刷新策略

```
提案状态变化触发（Event Listener）：
  ProposalCreated → 开始抓取数据
  VoteStarted     → 抓取 Snapshot + Forum
  VoteEnded       → 抓取最终票数
  ProposalExecuted → 抓取执行结果

定时任务（Cron）：
  每 5 分钟：检查新提案 + 轮询 Forum 新帖子
  每 1 分钟：检查 Discord 新消息（高优先级提案）
  每小时：更新投票进度（已投票率 / 票数分布）
```

## 4. AI 决策边界（Critical Design）

### 4.1 决策边界定义

这是整个设计最核心的部分——每个 AI 模块明确知道"什么是它能决定的，什么是它不能决定的"。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                     AI 决策边界图（Decision Boundary Map）                   │
│                                                                             │
│  AI 可以做 ✅                        AI 不能做 ❌                            │
│  ──────────                         ──────────                             │
│  读取 + 汇总 + 分析                  代替人做最终决策                        │
│  结构化呈现                          签署 / 投票                            │
│  风险评估（辅助信息）                修改原始提案内容                        │
│  投票建议（置信度说明）              决定预算分配                            │
│  社区情绪量化                        授权链上交易                            │
│  时间敏感性提醒                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 4.2 每个 AI 模块的边界

#### 模块 A：Summarizer（摘要生成）

**输入：** 提案正文（原始 Markdown，2000 字）
**输出：** 三段式摘要 + 一句话结论（< 500 字）

```
AI 可以做：
  ✅ 提取背景 / 变更内容 / 影响评估（结构化重组）
  ✅ 识别关键参数（数字、地址、合约名）
  ✅ 用非技术语言重写技术内容

AI 不能做：
  ❌ 添加原始提案中没有的信息（幻觉）
  ❌ 对提案的"好坏"做价值判断（只能描述客观内容）
  ❌ 修改提案原文（只能引用和转述）
```

#### 模块 B：Risk Assessor（风险评估）

**输入：** 提案内容 + 历史投票数据 + 作者地址信誉
**输出：** 风险矩阵（每个维度：低/中/高 + 说明）

```
AI 可以做：
  ✅ 基于已知风险模式分类（智能合约风险 / 市场风险 / 治理风险）
  ✅ 比对历史类似提案的结果
  ✅ 识别明显风险信号（无审计 / 预算异常 / 新合约部署）

AI 不能做：
  ❌ 代替专业审计机构做安全评估
  ❌ 预测市场走势（AI 不能预测价格）
  ❌ 判断"这个提案是否道德正确"
```

#### 模块 C：Vote Advisor（投票建议）

**输入：** 风险评估 + 社区情绪 + 用户历史投票倾向 + 投票建议请求
**输出：** 支持 / 反对 / 弃权 + 置信度（high/medium/low）+ 理由列表

```
AI 可以做：
  ✅ 给出有依据的建议（"基于 X 理由，建议支持"）
  ✅ 给出备选建议（"如果不确定，可以弃权"）
  ✅ 标注置信度（让用户知道 AI 对自己的建议有多确定）

AI 不能做：
  ❌ 代替用户投票（投票权法定属于代币持有者）
  ❌ 承诺执行结果（"投票通过后一定会有 X 效果"）
  ❌ 考虑用户的个人财务状况（AI 不知道用户的完整投资组合）
```

#### 模块 D：Community Sentiment（社区情绪）

**输入：** Forum 帖子列表 + Discord 消息 + 投票分布
**输出：** 情绪量化（正向/中性/负向百分比）+ 关键人物列表 + 未解决问题

```
AI 可以做：
  ✅ 统计情感倾向（正面/负面/中性的百分比）
  ✅ 识别有影响力的参与者（高声望 / 多追随者 / 核心开发团队）
  ✅ 提取未解决的关键问题（"这个问题在 Forum 里有 3 个人在问，但没人回答"）

AI 不能做：
  ❌ 判断"社区是否正确"（AI 不能判断群体智慧的准确性）
  ❌ 识别匿名马甲账号（链上地址不能证明是否是同一个人）
  ❌ 预测投票结果（只能基于当前数据，不能预测未来）
```

### 4.3 置信度系统

每个 AI 结论都附带置信度，分为三级：

| 置信度 | 含义 | 用户提示 |
|--------|------|---------|
| **high** | AI 有充分信息支撑结论，数据来源可靠且一致 | "置信度高，可以作为主要参考" |
| **medium** | AI 有部分信息支撑，存在数据空白或来源不一致 | "置信度中等，建议结合其他来源自行判断" |
| **low** | AI 缺乏足够信息，或数据来源不可靠 | "置信度低，仅作为初步参考，请务必阅读原文" |

**置信度降级触发条件：**
- Forum 数据不足（< 5 条帖子）→ 社区情绪置信度 → low
- 提案包含新合约部署（无审计报告）→ 风险评估置信度 → low
- 作者地址信誉未知 → 投票建议置信度 → low
- 多数据源结果不一致（Etherscan ↔ Alchemy 数据差 > 1%）→ 所有相关置信度 → medium

### 5.2 状态机（Proposal States）

| 状态 | 说明 | 用户通知 | AI 自动处理 |
|------|------|---------|-----------|
| `new` | 刚提交，待讨论 | 推送：新提案通知 | 抓取数据 + 生成摘要 |
| `discussion` | 讨论期（> 0 天）| 每日推送：讨论摘要更新 | 每日更新情绪分析 |
| `vote_started` | 投票已开始 | 推送：投票提醒（剩余 24h）| 生成投票建议卡片 |
| `vote_ending_soon` | 投票剩余 < 24h | 推送：紧急提醒 | 最后一次更新建议 |
| `vote_ended` | 投票结束 | 推送：结果速报 | 分析投票结果 |
| `passed` | 通过，待执行 | 推送：通过 + 时间锁倒计时 | 监控时间锁 + 跟踪执行 |
| `failed` | 未通过 | 推送：未通过简报 | 归档 + 更新用户投票历史 |
| `executed` | 已执行 | 推送：执行完成 + 结果验证 | 验证链上状态变更 |
| `canceled` | 被取消 | 推送：取消通知 | 归档 + 通知已投票用户 |

## 6. 标注示例：完整的人工确认标注

### 6.1 标注规范

每个输出模块明确标注以下信息：

| 标注类型 | 格式 | 含义 |
|---------|------|------|
| `✅ AI 自动化` | 模块直接输出，不带标注 | 标准处理流程 |

## 7. 失败处理（Failure Handling）

### 7.1 失败场景矩阵

| 失败场景 | AI 行为 | 用户通知 | 备选方案 |
|---------|---------|---------|---------|
| **Forum API 不可用** | 跳过社区情绪分析，输出其他模块 | "社区数据暂时不可，置信度降级" | 使用历史平均情绪估算 |
| **Snapshot 数据延迟** | 使用缓存数据 + 标注时间戳 | "票数数据可能有 5 分钟延迟" | 提示用户直接查看 Snapshot |
| **提案包含多语言内容** | 优先英文，检测到中文则切换双语摘要 | "检测到中文内容，已生成双语摘要" | 人工标记待翻译 |
| **Gas 估算失败**（新合约类型） | 标注"无法估算"，标记 `requires_audit: true` | "Gas 估算失败，请关注实际消耗" | 提供历史类似提案 Gas 数据参考 |
| **提案超出 AI 处理窗口**（超长正文 > 50K 字） | 分段处理：先处理摘要部分，其他部分标记"待详细分析" | "提案正文较长，部分分析可能不完整" | 提供分段查看入口 |
| **置信度全部 low**（数据严重不足） | 拒绝生成摘要，返回"数据不足以分析" | "数据不足以生成可靠摘要，请直接阅读原文" | 提供原文链接 + 基础信息（票数/状态） |

### 7.2 降级策略（Graceful Degradation）

```
正常模式（所有数据可用）
  → 完整摘要卡片（含风险评估 + 社区情绪 + 投票建议）

降级模式 1（Forum 数据缺失）
  → 摘要卡片（仅含背景/变更/影响）标注 ⚠️ community_sentiment: skipped

降级模式 2（Snapshot 数据延迟）
  → 标注 ⚠️ vote_data: possibly_stale（注明时间戳）

降级模式 3（多数据源不一致）
  → 标注 ⚠️ data_inconsistency：各来源分别显示，信任度权重分配

降级模式 4（完全无法分析）
  → 返回基础信息（标题 + 状态 + 票数）+ "AI 分析暂不可用"
```

### 9.1 核心技术栈

| 组件 | 技术选型 | 说明 |

| **部署** | Railway / Fly.io | 定时任务 + webhook 处理 |

### 9.2 AI Prompt 设计原则

每个 AI 模块的 prompt 设计遵循以下原则：

1. **角色设定**：明确 AI 是"分析助手"不是"决策者"
2. **边界声明**：prompt 开头声明"你不能做什么"
3. **输出格式**：强制 JSON schema，确保结构化输出
4. **置信度要求**：每个结论必须附带置信度和依据
5. **引用要求**：每个引用必须标注数据来源（post_id / address）

**示例 Prompt（Risk Assessor）：**

```
你是一个 DAO 治理风险评估助手。你的职责是根据提案内容分析风险，
不是替代人做决策。

你不能：
- 代替用户投票
- 承诺提案执行结果
- 对提案的道德或价值观做判断

输入：提案正文（JSON 格式）
输出：风险评估结果（严格 JSON schema，见下方）

每个风险维度必须包含：
- level: "low" | "medium" | "high"
- reason: 文字说明（< 100 字）
- requires_audit: boolean
- source: 引用来源（如 forum_post_3422）

如果数据不足，请在对应维度标注：
confidence: "low"，reason: "数据不足，无法可靠评估"
```

## 10. 总结：AI 与 Human 的边界设计原则

### 10.1 三条不可逾越的红线

```
❌ 红线 1：AI 不能代替任何人投票
   → 投票界面必须显示"这是您的个人决定，AI 建议仅供参考"

❌ 红线 2：AI 不能修改原始提案内容
   → AI 只能引用和转述，不能添加提案中没有的信息

❌ 红线 3：AI 不能承诺链上执行结果
   → "投票通过后 X 会发生" 是预测，不是事实
```

### 10.2 设计的核心价值

Proposal Summarizer 的价值不在于"AI 有多聪明"，而在于：

- **把人从信息过载中解放出来**：30 分钟 → 3 分钟
- **保留人的最终决策权**：AI 输出永远是辅助信息，不是指令
- **可追溯的置信度**：每个结论都标注来源和置信度，用户知道何时该信任、何时该怀疑
