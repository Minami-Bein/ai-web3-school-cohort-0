## Part 1：DAO 治理流程拆解

### 治理场景：Compound DAO 提案生命周期

```
提案发起 → 提案讨论 → 投票期 → 提案执行 → 执行后审计
    ↓          ↓          ↓          ↓          ↓
  AI 辅助    AI 辅助    AI 辅助    人工确认    AI 辅助
  摘要起草    舆情汇总    投票指引    时间锁     执行验证
```

### Step 拆解：每一步的 AI 与 Human 边界

| Step | 操作 | 能否自动化 | AI 辅助？ | 人工确认？ | 说明 |
|------|------|---------|---------|-----------|------|
| **1. 提案起草** | 发起人撰写提案文本 | ❌ | ✅ AI 辅助总结背景 | ✅ 必须人工签署 | 提案内容代表发起人立场，AI 不能代替签名 |
| **2. 提案提交** | 提交到 Governor 合约 | ❌ | ✅ AI 检查格式/字段 | ✅ 必须人工签名 | 链上签名代表真实身份，不可由 AI 代理 |
| **3. 讨论期（5 天）** | 社区 Forum + 链下讨论 | — | ✅ AI 实时汇总讨论要点 | ❌ | 汇总不是决策，不需要确认 |
| **4. 投票期（3 天）** | 代币持有者投票 | ❌ | ✅ AI 分析投票数据 + 给出建议 | ✅ 投票权属于代币持有者 | AI 不能代替人投票（法律层面），只能辅助分析 |
| **5. 提案通过** | Governor 合约状态变更为 "Succeeded" | ✅ 自动 | — | — | 合约自动执行，无人介入 |
| **6. 时间锁延迟（2 天）** | 等待时间锁窗口 | ✅ 自动 | ✅ AI 监控时间锁倒计时 | ❌ | 时间锁是安全机制，AI 可以监控并告警 |
| **7. 执行提案** | Governor 执行 `execute()` | ✅ 自动 | ✅ AI 验证执行结果 | ⚠️ 大额执行需多签确认 | 小额（< 10 ETH）等价值执行可自动；大额需人工授权 |
| **8. 执行后审计** | 验证状态变更是否符合提案 | — | ✅ AI 对比链上状态 vs 提案意图 | ⚠️ 争议时人工仲裁 | AI 发现差异才通知人工介入 |

## Part 2：Proposal Summarizer 草图

### 场景描述

TaxReportBot（Agent）作为 DAO 成员的个人助手，帮助用户快速了解 DAO 提案内容，并给出投票建议。

### Workflow

```
┌─────────────────────────────────────────────────────────────────────────┐
│                   Proposal Summarizer 工作流                            │
│                                                                        │
│  Snapshot 提案列表                                                      │
│       │                                                                │
│       ▼                                                                │
│  ┌─────────────┐     AI 辅助汇总     ┌─────────────────────┐           │
│  │ 原始提案文本 │ ───────────────→ │ 提案摘要卡片          │           │
│  │ (长文本)    │                   │ (200字结构化摘要)    │           │
│  └─────────────┘                    └─────────────────────┘           │
│                                              │                         │
│                                              ▼                         │
│                              ┌────────────────────────────┐           │
│                              │  投票建议 + 置信度           │           │
│                              │  ✅ 支持 / ❌ 反对 / 🤔 弃权  │           │
│                              └────────────────────────────┘           │
│                                              │                         │
│                                              ▼                         │
│                              ┌────────────────────────────┐           │
│                              │  风险提示 + 替代方案        │           │
│                              │  （高风险提案额外标注）      │           │
│                              └────────────────────────────┘           │
└─────────────────────────────────────────────────────────────────────────┘
```

### AI 辅助总结的内容（✅ AI 可以做）

| 内容块 | 说明 | 自动化？ |
|--------|------|---------|
| **提案摘要** | 背景 / 目的 / 主要变更，三段式结构 | ✅ AI 生成 |
| **历史投票模式** | 此地址过去的投票倾向（支持/反对/弃权比例） | ✅ AI 读取链上数据 |
| **社区情绪分析** | Forum / Twitter / Discord 的讨论倾向 | ✅ AI 汇总（情感分析） |
| **风险评估** | 合约风险 / 代币经济风险 / 治理风险（高/中/低） | ✅ AI 评估 |
| **Gas 成本估算** | 执行提案预估 Gas 消耗 | ✅ AI 调用 `eth_estimateGas` |
| **时间锁倒计时** | 提案通过后距离执行还有多久 | ✅ AI 监控 |

### 人工确认的内容（❌ AI 不能决定）

| 内容块 | 说明 | 为什么需要人 |
|--------|------|------------|
| **投票决定** | 最终支持/反对/弃权 | 投票权是代币持有者的法定权利，AI 不能代理投票 |
| **利益冲突声明** | 投票者是否与提案有利益关联 | AI 无法判断人类的个人利益 |
| **提案修改意见** | 对提案文本的修改建议 | 修改提案需要人的意志表达 |
| **执行授权（大额）** | 超过阈值的执行需要多签确认 | 资产处置必须由人决定 |

### Proposal Summarizer 输出示例

```
📋 提案摘要卡片
```

## Part 3：Meeting-to-Action Workflow 草图

### 场景描述

DAO 线下/线上会议结束后，TaxReportBot 自动从会议记录（Meeting Notes）提取 Action Items，并生成对应的链上提案草稿。

### Workflow

```
会议结束（Notion / Google Docs 记录）
        │
        ▼
┌──────────────────────┐
│  原始会议记录文本     │
│  （议程 + 讨论 + 决策）│
└──────────┬───────────┘
           │
           ▼
   ┌──────────────┐
   │  AI 提取      │  ✅ AI 自动化
   │  - 决策列表   │
   │  - Action Items│
   │  - 负责人     │
   │  - 截止日期   │
   └──────┬───────┘
          │
          ▼
   ┌────────────────────────┐
   │  AI 生成草稿            │  ⚠️ 部分自动化
   │  - 决策理由（摘要）     │    AI 生成草稿
   │  - 链上执行步骤         │    人确认内容后提交
   │  - 预算需求（如果有）   │
   └──────┬─────────────────┘
          │
          ▼
   ┌─────────────────────────────────┐
   │  人工确认区                       │  ❌ 必须人工
   │  - 决策是否符合社区利益          │
   │  - 预算是否合理                  │
   │  - 是否同意作为正式提案提交      │
   └──────┬──────────────────────────┘
          │
          ▼
   ┌──────────────────────┐
   │  正式提案             │  ✅ 自动提交到 Snapshot
   │  （用户签署后提交）   │
   └──────────────────────┘
```

### AI 提取 vs 人工确认的边界

| 步骤 | 内容 | 自动化？ | 人工确认？ |
|------|------|---------|-----------|
| **提取决策** | 从会议记录中识别"决定了什么" | ✅ AI 提取 | ⚠️ 确认决策内容是否准确 |
| **提取 Action Items** | 从讨论中识别"谁做什么、什么时候做完" | ✅ AI 提取 | ✅ 负责人自行确认 |
| **生成提案草稿** | 把决策转化为链上提案格式（标题/摘要/执行计划） | ✅ AI 生成草稿 | ✅ 必须确认后才提交 |
| **估算 Gas 成本** | 提案执行预计消耗多少 Gas | ✅ AI 计算 | ❌ 不需要确认 |
| **预算草案** | 提案是否涉及资金动用，多少 | ✅ AI 计算 | ✅ 必须人工审核预算 |
| **提交提案** | 将草稿正式提交到 Governor/Snapshot | ❌ | ✅ 必须人工签名提交 |
| **设置投票提醒** | 投票开始/结束前通知相关人 | ✅ AI 自动设置 | ❌ |

### Meeting-to-Action 完整流程

```
会议记录输入
    │
    ▼
Step 1：AI 结构化解析
    │
    ├── 决策列表（Decisions）
    ├── 行动项列表（Action Items）
    ├── 涉及资金？（Budget Change？）
    └── 风险点（Risks）
    │
    ▼
Step 2：AI 生成摘要（不涉及链上操作）
    │
    ├── 决策摘要（3 句话）
    ├── Action Items 表格
    └── 风险评估（高/中/低）
    │
    ▼
Step 3：人工审核（Notion / 邮件 / Telegram）
    │
    ├── 负责人确认 Action Item
    ├── 预算委员会审核预算（如有）
    └── 核心成员确认决策内容
    │
    ▼
Step 4：AI 生成链上提案草稿
    │
    ├── 提案标题 + 摘要（基于决策）
    ├── 执行步骤（基于 Action Items）
    ├── 预算请求（如果有）
    └── 时间锁计划（基于预算大小）
    │
    ▼
Step 5：人工签署 + 正式提交
    │
    └── 用户签名 → 提案上链
    │
    ▼
Step 6：AI 监控 + 结果回写
    │
    ├── 提案状态跟踪（讨论期→投票期→通过）
    ├── 投票结果通知
    └── 执行后验证 + 记录到 Notion
```

## Part 6：关键设计原则

### AI × DAO 治理的核心边界

**AI 可以做的：**
- ✅ 快速读取和汇总链上/链下数据（提案文本、投票历史、讨论帖）
- ✅ 结构化呈现复杂信息（摘要卡片、Action Items 表格）
- ✅ 监控提案状态、执行结果、时间锁倒计时
- ✅ 风险评估和投票建议（辅助信息，不是决策）

**AI 不能做的：**
- ❌ 代替人投票（代币持有者是法定投票人）
- ❌ 签署提案（链上签名代表真实身份和法律责任）
- ❌ 修改提案内容（需要人的意志表达）
- ❌ 决定预算分配（预算是 DAO 最重要的权力）
- ❌ 判断利益冲突（个人利益只能由本人声明）

**为什么这个边界是 AI × Web3 特有的？**

在传统 SaaS 中，AI 辅助决策不需要区分"AI 分析"和"AI 决策"——因为没有链上身份和资产风险。

但在 DAO 治理中：
1. **链上签名有法律含义**：在 Governor 合约上的投票签名代表代币持有者的真实意图，不能由 AI 代理
2. **资金通过合约流动**：预算决策如果由 AI 自动执行，一旦出错无法撤回（不可逆性）
3. **声誉机制依赖人类判断**：贡献质量、信任程度是主观判断，需要人来认定

## Part 8：为什么 DAO Governance 是 AI × Web3 的核心交叉问题

### 为什么不是纯 AI 问题？

DAO 治理的核心不是"AI 分析得更准"——而是**权力分配和责任归属**：

- 投票权是**法定权利**，不是技术能力，不能被 AI 替代
- 预算决策涉及**真实资产**，AI 可以辅助分析但不能决定分配
- 争议解决需要**人的判断**（法律、道德、利益冲突）

### 为什么不是纯 Web3 问题？

传统 DAO 工具（Tally、Snapshot、Zodiac）解决了"怎么投票"，但没有解决：

- **信息过载**：一个活跃 DAO 可能有上百个提案，人工阅读成本极高
- **执行监控**：提案通过后谁来监控执行？出了问题谁负责？
- **贡献量化**：贡献数据分散在多个平台（链上、Forum、Discord），聚合成本高

这些是**信息处理和决策支持**的问题，AI 天然适合解决。

### 核心交叉价值

DAO Governance 需要 AI 做"**信息层**"的工作——快速读取、汇总、分析、监控——把人从信息过载中解放出来，让人专注在**必须由人做的决策**上。

没有 AI，DAO 成员每天需要花数小时阅读提案和讨论；没有 Web3，AI 的分析结论无法以密码学方式强制执行。
